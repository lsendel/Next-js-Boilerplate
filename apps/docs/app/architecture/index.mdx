# Architecture Overview

The Next.js Boilerplate follows a clean, layered architecture with clear separation of concerns and strong type safety throughout.

## Core Principles

### 1. Layer-Based Organization

Code is organized by execution environment and responsibility:

```
┌─────────────────────────────────────────┐
│         /app (Next.js App Router)       │
│       Pages, Layouts, API Routes        │
└───────────────┬─────────────────────────┘
                │
      ┌─────────┴──────────┐
      │                    │
      ▼                    ▼
┌──────────┐          ┌──────────┐
│ /client  │          │ /server  │
│Components│          │ Database │
│  Hooks   │          │ Services │
│Providers │          │   API    │
└─────┬────┘          └─────┬────┘
      │                     │
      └──────────┬──────────┘
                 ▼
           ┌───────────┐
           │  /shared  │
           │   Types   │
           │   Utils   │
           │Validators │
           └───────────┘
```

### 2. Dependency Direction Rules

**Strict unidirectional dependencies:**

- ✅ `/app` CAN import from any layer
- ✅ `/client` CAN import from `/shared`
- ✅ `/server` CAN import from `/shared`
- ❌ `/client` CANNOT import from `/server`
- ❌ `/shared` CANNOT import from `/client` or `/server`

### 3. Type Safety First

- **TypeScript strict mode** enabled
- **T3 Env** for type-safe environment variables
- **Zod schemas** for runtime validation
- **DrizzleORM** for type-safe database queries
- **Type-safe routing** with next-intl

### 4. Colocation

Related files are kept together:
- Tests next to source (`.test.ts`, `.test.tsx`)
- Stories next to components (`.stories.tsx`)
- Styles with components (CSS-in-JS or Tailwind)

### 5. No Circular Dependencies

The build will fail if circular dependencies are detected, ensuring clean architecture.

## Request Flow

### Server-Side Rendering (SSR)

```
1. User Request → Next.js
2. Middleware Pipeline
   ├── Tenant Resolution
   ├── Security (Arcjet)
   ├── Authentication
   └── i18n Routing
3. Page/Layout Server Component
4. Data Fetching (Server)
   ├── Database Query (Repository)
   └── External APIs (Service)
5. Component Rendering
6. HTML Response
```

### API Request

```
1. API Request → Next.js API Route
2. Middleware Pipeline
   ├── Security (Arcjet)
   ├── Rate Limiting
   └── Authentication
3. Controller
   ├── Validation (Zod)
   └── Business Logic (Service)
4. Service
   └── Data Access (Repository)
5. JSON Response
```

### Client-Side Navigation

```
1. User Interaction
2. Client Component
3. API Call (fetch/SWR)
4. State Update
5. Re-render
```

## Design Patterns

### Repository Pattern

**Data access abstraction:**

```typescript
// Repository (data access)
class UserRepository {
  async findById(id: string) {
    return db.query.users.findFirst({ where: eq(users.id, id) })
  }
}

// Service (business logic)
class UserService {
  async getUser(id: string) {
    const user = await userRepository.findById(id)
    if (!user) throw new Error('User not found')
    return user
  }
}

// Controller (HTTP handling)
async function GET(request: Request) {
  const user = await userService.getUser(userId)
  return Response.json(user)
}
```

### Factory Pattern

**Authentication provider abstraction:**

```typescript
// Factory creates provider instance
const authProvider = AuthFactory.getProvider()

// Unified API works with any provider
const user = await authProvider.getCurrentUser()
```

### Adapter Pattern

**Provider-specific implementations:**

```typescript
// Each provider implements the same interface
class ClerkAdapter implements AuthAdapter {
  async getCurrentUser() { /* Clerk-specific */ }
}

class CloudflareAdapter implements AuthAdapter {
  async getCurrentUser() { /* Cloudflare-specific */ }
}
```

### Dependency Injection

**Services receive dependencies:**

```typescript
class EmailService {
  constructor(
    private userRepository: UserRepository,
    private logger: Logger
  ) {}
}
```

## Best Practices

### Code Organization

✅ **DO:**
- Use absolute imports (`@/`)
- Colocate related files
- Follow naming conventions
- Keep components small and focused
- Separate concerns (data, logic, UI)

❌ **DON'T:**
- Use relative imports (`../../`)
- Create circular dependencies
- Mix client and server code
- Create god components
- Bypass type safety with `any`

### Performance

✅ **DO:**
- Use Server Components by default
- Add `'use client'` only when needed
- Lazy load heavy components
- Optimize images
- Minimize bundle size

❌ **DON'T:**
- Make everything a Client Component
- Import large libraries on client
- Skip image optimization
- Ignore bundle size

### Security

✅ **DO:**
- Validate all input (Zod)
- Use parameterized queries
- Implement CSRF protection
- Rotate sessions
- Use security headers

❌ **DON'T:**
- Trust user input
- Use string interpolation in queries
- Skip authentication checks
- Store secrets in code
- Disable security features
